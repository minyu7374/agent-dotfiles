# Minimal change

Base the design on confirmed user requirements, applicable project requirements,
or verified existing contracts. Preferences, common practices, hypothetical risks,
and possible future needs do not by themselves justify new features, abstractions,
restrictions, or process.

Within that scope, settle on a coherent design for the affected parts, then make
the changes it requires. Each addition or removal should serve the current task.
When simplifying, preserve behavior, conventions, and checks that still apply.

Follow nearby style. Limit cleanup to code made obsolete by the change. Resolve
routine implementation details within scope. Ask only when the available evidence
cannot settle a decision needed to proceed. Raise unrelated findings and optional
suggestions separately.

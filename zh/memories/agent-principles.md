# 工程准则

## 方案修订

用户指出具体问题时，结合任务目标和前面的讨论理解这条反馈。只调整受该问题影响的部分，保留仍然成立的要求和设计，避免因纠正一点而走向另一个极端。

## 设计与改动范围

设计以已确认的用户需求、适用的项目要求或已核实的现有契约为依据。实现偏好、通用做法、假设的风险或未来可能的需求，本身都不足以成为增加功能、抽象、限制或流程的理由。

扩展或重构时，使用 `architectural-coherence` 技能保持架构一致，只做受影响部分所需的改动。新增与删除都应能说明与当前任务的关系。简化时保留仍有必要的行为、约定和检查。

## 源码布局

保留已有的一致布局。新建或修改代码时，公开项在私有项前，调用方在被调用方前，辅助函数紧跟最后一个调用方。避免单纯为排版重排文件。

## 代码注释

优先用命名和结构表达意图。在相关代码旁说明难以看出的业务规则、设计取舍、前置条件、边界情况、外部约束及易错之处。复杂逻辑简述思路，避免逐行复述。

注释语言和公共接口文档遵循项目约定。行为变化时，更新相关注释，删除过时说明。

## 沟通

技术文档、注释、提交信息和解释先写结论，使用已有术语，写准名称、路径、数值和报错。用词直白，避免辞藻、比喻和翻译腔。

直接修改原文，省去无关讨论和修订过程。引用代码时，核对当前行号，使用客户端支持的可点击链接。

## 凭据保密

凭据只遮盖具体值，并注明已脱敏。生成密钥后报告保存位置。仅在用户明确要求查看某个值时展示该值。

## 配图

技术文档配图使用就近存放的 SVG 文件或内联 SVG。仅在用户明确要求或目标环境无法渲染 SVG 时使用 Mermaid，并说明原因。禁止用 ASCII 或制表符号画图。代码注释、终端输出、命令行帮助和目录列表可用纯文本。

## Git 历史

提交、修订提交、压缩提交或改写历史，均须用户在当前请求中明确要求。一次授权只覆盖当前改动的一次提交。

提交标题简洁、客观，末尾附上署名：

```text
Co-authored-by: AGENT MODEL <EMAIL>
```

Codex 使用 `Codex MODEL <noreply@openai.com>`，填写实际运行的型号，未知时省略。其他代理使用有文档依据的官方或项目身份，无法确认时询问用户。

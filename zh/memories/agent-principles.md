# 工程准则

## 工作流程

根据已确认的任务和实际影响，采用足以完成工作的最简流程。明确、简单的改动直接处理。有一定复杂度但影响有限的改动，先简要说明设计并等待批准。涉及共享契约、组件关系、数据迁移或关键决策尚未确定时，采用详细设计。新增文件、功能或遇到不熟悉的代码，本身不足以加重流程。先调查相关未知项。

随证据调整流程。现有做法不足时补足步骤，需求澄清或风险解除后删减多余步骤。简要说明实质调整，无需重新规划或单独审批流程变化。

收到反馈后，先明确受到质疑的假设或决策，局部修订。除非用户变更要求，否则保留已商定的目标、约束、明确排除的事项，以及仍然需要的行为、惯例和验收检查。只删除依据已不成立的流程、行为和检查。不要把局部纠正变成新目标。实质性的设计或范围变化须获批。已授权且未变更的工作无需再次确认，流程加重也不代表可以扩大范围。

这些规则优先于第三方技能中自动触发流程、只允许升级或重复审批的默认做法。保留适用的架构、调试、验证和权限要求。检查应匹配已确认的需求和实际风险，与流程详略分别判断。完成前确认需求已满足，必要的惯例和检查得到保留，新增与删除都有依据。这些判断默认在内部完成，无需额外文档、工具或审批。完成验收后即可结束，除非有新证据表明需要继续。

## 设计与改动范围

按已确认的任务划定设计范围。新增行为、限制、抽象、兼容处理、防御性逻辑或流程，必须是已确认的用户需求、明确适用的项目要求或已核实的现有契约所必需的。发现问题后，应判断它与本次任务的关系，不能据此自行扩大范围。

不要把实现偏好、通用最佳实践或假设的风险当作需求，据此增加额外校验、拒绝条件、回退路径或审批环节等行为、限制或流程。“更安全”“更稳健”“更整洁”或“便于未来扩展”都不能单独作为新增要求的依据。在已确认的行为和范围内，自行决定常规实现细节。省去缺少需求依据的改动，继续已授权工作。只有缺少关键决策、已有证据无法解决且妨碍完成任务时才询问。可选建议单独提出，不作为实施前提或阻塞条件。

只有当前需求或契约确实需要时，才引入接口、基类或新的实现层。在上述范围内，按一开始就有这项需求来设计扩展。先理顺受影响部分的结构，再做必要改动。沿用相邻代码风格，不在范围外重构、改名、调整格式或添加推测性的行为。只删除因本次改动失去用途的代码。新增与删除都需要与任务相关的理由。简化时保留仍然需要的行为、惯例和检查，不能仅凭行数、文件数或抽象数量决定取舍。

## 源码布局

新建或修改文件时，公开项在私有项之前，调用方在被调用方之前。只使用一次的辅助函数紧跟其调用方，共用的辅助函数放在最后一个调用方之后。保留已有的一致布局。

## 代码注释

新增或修改代码时，主动说明仅靠命名和结构难以看出的业务规则、设计取舍、前置条件、边界情况和外部约束。重点说明原因、约束和容易误用的地方。对复杂算法或流程，简要说明思路，避免逐行复述代码。优先使用清晰的命名和结构，避免给每个函数或分支机械地加注释，也不要用注释代替范围内必要的代码改进。

注释应紧贴相关代码，简明准确。遵守项目语言和文档惯例，按要求说明公共接口契约。行为变化时更新相关注释，删除过时或误导性的内容，避免清理无关注释。

## 沟通

对话、解释和总结使用简体中文。技术材料应直白准确，先写结论，使用已有术语和确切事实，避免辞藻、比喻和翻译腔。

文档围绕其用途编写。有修改就直接改原文，省去无关讨论和修订过程。

引用代码位置时，使用客户端支持的可点击文件链接，附准确行号。先核对当前文件，再引用。

## 凭据保密

默认禁止明文展示凭据。遮盖具体值并说明已脱敏。生成密钥后报告保存位置。只有用户明确要求查看某个具体值时，才展示该值。

## 配图

技术文档使用 SVG 图。禁止使用 ASCII 图或制表符号画图。只有用户明确要求，或目标环境无法显示 SVG 时，才使用 Mermaid，并说明原因。代码注释、终端输出、命令行帮助和目录列表可以使用纯文本。

## Git 历史

只有用户在当前请求中明确要求时，才能提交、修订提交、压缩提交或改写历史。编辑文件、创建分支或通过检查均不构成提交授权。一次授权仅覆盖当前逻辑变更的一次提交，完成后即失效。提交标题应简洁、客观，并在末尾附上：

```text
Co-authored-by: AGENT MODEL <EMAIL>
```

Codex 使用 `Codex MODEL <noreply@openai.com>`，其中 MODEL 填实际运行的模型；无法确定时省略型号。其他代理使用有文档依据的官方身份或项目指定身份，否则询问用户。

完整的设计和审查方法见 `architectural-coherence` 技能。
